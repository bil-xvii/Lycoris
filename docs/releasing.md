# Выпуск обновления MONOLITH (для владельца)

Цель: вы что-то изменили у себя — у всех пользователей в программе появляется кнопка **«ОБНОВЛЕНИЕ x.y.z»**, они нажимают
«обновить» прямо в MONOLITH, и новая версия ставится сама.

## Как это устроено

```
вы:  поднимаете <Version> → пишете RELEASE_NOTES.md → tools\release.ps1
                                         │
          публичный репозиторий bil-xvii/MONOLITH-releases  ← сюда кладутся MONOLITH.exe и MONOLITH.exe.sha256
                                         │  (анонимный запрос: api.github.com/repos/bil-xvii/MONOLITH-releases/releases/latest)
пользователь:  MONOLITH раз в 12 часов (и по кнопке «ПРОВЕРИТЬ ОБНОВЛЕНИЯ») спрашивает последний релиз
               → версия новее своей? → кнопка «ОБНОВЛЕНИЕ x.y.z» в заголовке и блок в «Настройки → О программе»
```

Приложение **никогда** не ходит в закрытый репозиторий `bil-xvii/MONOLITH` и не использует токены: проверяется только публичный
репозиторий релизов (лимит GitHub для анонимных запросов — 60 в час, приложение делает 1 запрос в 12 часов и использует ETag).
Предрелизы (`prerelease`) и черновики (`draft`) пользователи не видят.

## Единственный источник номера версии

`<Version>1.0.0</Version>` в `src/Monolith/Monolith.csproj`. Из него берутся: версия в файле (свойства exe), строка в заголовке
окна, «О программе», сравнение «есть ли новее» и тег релиза `vX.Y.Z`. Больше нигде номер вручную не правится
(`AssemblyVersion`/`FileVersion` вычисляются сами). `tools\publish.ps1` в конце печатает версию.

Номер — только `x.y.z` (например `1.0.1`). Правило: **каждый выпуск строго больше предыдущего**, иначе пользователи
ничего не увидят, а `release.ps1` откажется работать.

## Шаги выпуска

1. Закончите работу, закоммитьте и **запушьте** (`tools\autosave.ps1` делает это сам). Дерево должно быть чистым.
2. Поднимите версию в `src/Monolith/Monolith.csproj`: `1.0.0` → `1.0.1`, закоммитьте и запушьте.
3. В `RELEASE_NOTES.md` добавьте раздел `## 1.0.1` с короткими пунктами «что нового». Первые ~15 строк раздела
   пользователь увидит в «Настройки → О программе».
4. Пробный прогон (ничего не собирает и не публикует, только проверки и план):
   ```
   powershell -ExecutionPolicy Bypass -File tools\release.ps1 -WhatIf
   ```
5. Настоящий выпуск (нужны: GitHub CLI `gh` с входом `gh auth login`, права на оба репозитория):
   ```
   powershell -ExecutionPolicy Bypass -File tools\release.ps1
   ```
   Скрипт по порядку и **останавливается на первой ошибке**:
   - версия из csproj строго больше последнего релиза в `bil-xvii/MONOLITH-releases`, тега ещё нет;
   - рабочее дерево чистое, HEAD уже в `origin`;
   - в `RELEASE_NOTES.md` есть непустой раздел этой версии;
   - `dotnet test` зелёный;
   - `tools\publish.ps1` собирает `publish\MONOLITH.exe` (и подписывает, если на этом ПК есть сертификат — `docs/signing.md`);
   - `publish\MONOLITH.exe --selftest` завершается с кодом 0;
   - пишет `publish\MONOLITH.exe.sha256` (`<хеш>  MONOLITH.exe`);
   - `gh release create vX.Y.Z` в `bil-xvii/MONOLITH-releases` (публичный, **отсюда берут пользователи**) и в `bil-xvii/MONOLITH`
     (закрытый, тег на этом коммите) — оба с `MONOLITH.exe`, `MONOLITH.exe.sha256` и текстом из `RELEASE_NOTES.md`.
6. Проверка: на другом ПК (или у себя после `Настройки → О программе → ПРОВЕРИТЬ ОБНОВЛЕНИЯ`) должна появиться
   кнопка «ОБНОВЛЕНИЕ 1.0.1».

Имена файлов в релизе должны быть ровно `MONOLITH.exe` и `MONOLITH.exe.sha256` — приложение ищет их по имени.
Если `.sha256` забыт, приложение всё равно сверяет файл с «digest», который GitHub сам считает для каждого файла; если нет
ни того ни другого — обновление отклоняется.

## Что видит и что делает пользователь

1. В заголовке окна — белая кнопка **«ОБНОВЛЕНИЕ 1.0.1»**; в «Настройки → О программе» — установленная/последняя версия,
   «что нового» и кнопки «ОБНОВИТЬ СЕЙЧАС», «ПРОВЕРИТЬ ОБНОВЛЕНИЯ», «НАПОМНИТЬ ПОЗЖЕ» (на сутки), «ПРОПУСТИТЬ ЭТУ ВЕРСИЮ»
   (следующую новую покажет снова). Автопроверку можно выключить (по умолчанию включена).
2. Нажатие открывает подтверждение: версия, размер, источник (`github.com/bil-xvii/MONOLITH-releases`), чем проверяется файл,
   что программа перезапустится, что настройки и журнал сохранятся.
3. Если в это время выполняется установка/изменение/очистка/ремонт или идёт игровой сеанс — обновление **не запускается**, причина
   показана текстом и есть кнопка «ПОВТОРИТЬ». Запущенные задачи обновление не прерывает.
4. Загрузка с процентами и «ОТМЕНА» → проверка → программа закрывается (журнал сохраняется как при обычном закрытии) →
   запускается новая версия.

## Как заменяется работающий exe (и почему это безопасно)

Работающий однофайловый `MONOLITH.exe` **никогда не перезаписывается на месте** (CLAUDE.md). Порядок:

1. Скачанный файл проверен: HTTPS, адрес только `github.com/bil-xvii/MONOLITH-releases/releases/download/…` (после перенаправлений —
   `objects.githubusercontent.com` / `release-assets.githubusercontent.com`; каждый переход проверяется **до** запроса),
   размер 40–300 МБ, SHA-256 по `.sha256` и по digest GitHub (если оба есть — должны совпасть), заголовок PE x64,
   подпись Authenticode (если exe подписан — новый обязан быть подписан тем же издателем).
2. Старая копия кладёт новый exe рядом: `MONOLITH.exe.new` (папка недоступна для записи, например `Program Files` —
   запускает его прямо из `%LocalAppData%\MONOLITH\Updates` с запросом UAC). Перед запуском файл открывается так, что никто
   не может его изменить, и хеш сверяется ещё раз.
3. Запускается новый exe в режиме `--apply-update <старый exe> <pid>` (без окна): ждёт закрытия старой копии (до 60 с),
   переименовывает `MONOLITH.exe` → `MONOLITH.exe.old` (хранится одна копия), **копирует** себя в `MONOLITH.exe`, запускает его и 10 секунд
   наблюдает.
4. Если новая версия не запустилась или упала с кодом ошибки — `MONOLITH.exe.old` возвращается на место и запускается снова.
   Если вернуть не удалось — пользователю показывается сообщение, где лежит `.old`.
5. Через минуту после успешного старта новая версия удаляет `.old`, `.new` и скачанные файлы в `Updates`.

Сбои, при которых у пользователя остаётся рабочая программа: нет сети/лимит GitHub (молча, без ошибок), не совпал хеш/подпись
(файл удаляется), диск переполнен, закрылась не сразу (ждём 60 с, иначе ничего не меняем), антивирус держит файл (повторы 5 раз
по 0,5 с, потом «ничего не изменено»), UAC отклонён, новая версия падает (откат). Особые случаи: запуск с сетевого диска или
диска только для чтения — программа честно пишет, что на месте обновить нельзя, и даёт ссылку на страницу релизов; сборка для
разработки (несколько файлов) не обновляется; портативная копия на рабочем столе обновляется как обычно.

## Если что-то пошло не так у вас

- `release.ps1` отказал — прочитайте строку `REFUSED:`; обычно версия не поднята, дерево не чистое или нет раздела в `RELEASE_NOTES.md`.
- Нужно отозвать плохой выпуск: на странице релизов в `MONOLITH-releases` пометьте его `Pre-release` или удалите
  (приложение смотрит только «latest, не предрелиз») и выпустите исправление с большим номером. **Откатов номера назад
  приложение не делает** — оно предлагает только более новую версию.
- Проверка без публикации: `tools\release.ps1 -WhatIf`.
