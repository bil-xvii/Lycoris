# Как быстро и качественно писать код с ИИ-агентами (свод официальных руководств)

Источники (все страницы прочитаны):
- CC-BP = [Anthropic — Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- CC-WF = [Anthropic — Common workflows](https://code.claude.com/docs/en/common-workflows)
- BEA = [Anthropic — Building effective AI agents](https://www.anthropic.com/engineering/building-effective-agents)
- OAI = [OpenAI — Best practices (Codex docs)](https://learn.chatgpt.com/guides/best-practices)
- AMD = [agents.md — AGENTS.md](https://agents.md)
- GH = [GitHub — Best practices for using Copilot to work on tasks](https://docs.github.com/en/copilot/tutorials/coding-agent/get-the-best-results)
- GEM = [Google — Gemini CLI: GEMINI.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md), [Gemini CLI — Plan Mode](https://geminicli.com/docs/cli/plan-mode)
- GOO = [Google — Small CLs (eng-practices)](https://google.github.io/eng-practices/review/developer/small-cls.html)

Пометка «(1 компания)» = правило даёт только одна компания.

## Правила

1. **Дай агенту проверку pass/fail (тесты, build, линтер) и требуй её запуск.**
   Почему: без проверки у агента есть только «выглядит готово», и тестом становишься ты.
   Источники: CC-BP, OAI, AMD, BEA (ground truth от среды).

2. **Порядок: исследовать -> план -> код -> проверить. Для неоднозначных/многофайловых задач сначала Plan mode.**
   Почему: согласовать подход дешевле, чем переделывать код.
   Источники: CC-WF (plan mode), OAI (/plan), GEM (Plan Mode), GH (план до PR).

3. **Ставь задачу конкретно: цель, контекст (файлы, ошибка), ограничения, условие «готово когда».**
   Почему: агент не видит того, что есть только в твоей голове; это экономит круг правок.
   Источники: CC-BP, OAI, GH.

4. **Называй файлы и образец: «сделай по аналогии с X.cs, без новых библиотек».**
   Почему: образец и ограничения убирают гадание о стиле и зависимостях.
   Источники: CC-BP, GH.

5. **Для ошибок давай команду воспроизведения, стек и шаги; проси сначала падающий тест, потом фикс.**
   Почему: агент замыкает цикл сам и доказывает, что баг исправлен.
   Источники: CC-WF, CC-BP.

6. **Держи диффы маленькими и самодостаточными: одна вещь за изменение, тесты вместе с кодом.**
   Почему: быстрее и тщательнее ревью, меньше багов, легче откат.
   Источники: GOO, CC-WF (рефакторинг малыми проверяемыми шагами), GH (узкие задачи).

7. **Файл контекста (CLAUDE.md / AGENTS.md / GEMINI.md) коротким и живым: команды build/test/lint, подводные камни, решения, которых нет в коде.**
   Почему: каждая строка забирает внимание на каждой задаче; то, что агент прочтёт в коде сам, не пиши.
   Источники: CC-BP, OAI, AMD, GEM, GH.

8. **Добавляй правило в файл контекста только после повторной ошибки; не пихай туда архитектуру и CAPS.**
   Почему: раздутый файл теряет строки, акцент заставляет агента переприменять правило.
   Источники: CC-BP, OAI.

9. **Разделяй файлы по областям: глобальный -> репозиторий -> подпапка, ближайший главнее; разовые инструкции выноси в отдельные md/skills.**
   Почему: нужный контекст грузится только там, где работаешь.
   Источники: OAI, AMD, GEM, CC-BP, GH.

10. **Параллельная работа: у каждой сессии свой git worktree; независимые куски отдавай субагентам.**
    Почему: правки не конфликтуют, ты занят своим, а не наблюдаешь за агентом.
    Источники: CC-WF, CC-BP, OAI, BEA (параллелизация).

11. **Исследование и шумный вывод делегируй субагенту, а главному агенту оставь основную задачу.**
    Почему: в основной контекст возвращаются только выводы. Делегирование само по себе ответ не улучшает.
    Источники: CC-WF, OAI, CC-BP.

12. **Ревью делай «свежим» взглядом (новый контекст/субагент) против спеки; в промпте ревью пиши «стиль пропусти».**
    Почему: ревьюер, который писал код, предвзят; ищущий проблемы всегда что-то найдёт и раздует код.
    Источники: CC-BP, OAI (/review, code_review.md), GH (PR как от обычного контрибьютора).

13. **Требуй доказательство: команду и её вывод, а не «всё проходит».**
    Почему: для сессии без твоего присмотра это единственная улика.
    Источник: CC-BP (1 компания); близко OAI («подтверди финальное поведение»).

14. **Следи за первой минутой: Esc при отклонении; после двух неудачных поправок /clear и новый точный промпт.**
    Почему: третья поправка копится на двух провалах в контексте.
    Источник: CC-BP (1 компания); OAI: один чат на одну связную единицу работы.

15. **Для правил без исключений используй детерминизм (hook, deny-правило, права), а не просьбу в тексте.**
    Почему: промпт и файл контекста агент читает «обычно», хук выполняется всегда.
    Источник: CC-BP (1 компания); OAI/GH: начинай с осторожных прав.

16. **Сначала простейшее решение; усложняй (агенты, цепочки) только если измерение показало пользу. Ставь лимиты итераций и человеческие точки контроля.**
    Почему: агенты дороже и накапливают ошибки.
    Источник: BEA (1 компания).

17. **Если задача размыта, пусть агент проинтервьюирует тебя и запишет SPEC.md; строй из него в чистой сессии.**
    Почему: письменное «готово когда» и чистый контекст.
    Источники: CC-BP, OAI (interview).

18. **Подбирай задачи по силам: агенту отдавай ограниченные баги, тесты, доку, техдолг; сложное, размытое и чувствительное делай сам. Уровень reasoning по сложности задачи.**
    Почему: так меньше брака.
    Источники: GH, OAI.

## Чего руководства советуют НЕ делать

- Не оставлять без команд сборки/тестов и не просить «проверь» без способа проверки (OAI, CC-BP, AMD).
- Не писать долгоживущие правила только в промпте и не пропускать план на многошаговой задаче (OAI).
- Не гонять живые задачи по одним и тем же файлам без worktree и не давать полные права, пока не понял процесс (OAI, CC-BP).
- Не раздувать файл контекста и не дублировать в нём то, что видно в коде; не лечить игнор строки словом IMPORTANT (CC-BP, OAI).
- Не отдавать агенту огромные размытые задачи и огромные диффы (GH, GOO); не вести весь проект в одном чате (OAI).
